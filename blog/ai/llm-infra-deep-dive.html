先按这条主线学习

第一步：语言模型先通过 next-token prediction 学会“给定前文预测下一个 token”。如果这一步不懂，后面的 loss、softmax、采样都容易变成死记。

第二步：Transformer 用 attention 解决“上下文里哪些 token 重要”的问题，所以才能比传统 RNN 更适合大规模并行训练。

第三步：模型越大，单卡放不下、训练太慢，于是出现 TP、PP、ZeRO/FSDP 这些“拆模型、拆状态、拆计算”的方法。

第四步：模型上线后，自回归逐 token 生成导致推理慢、KV Cache 占显存、请求长短不一导致 GPU 空转，于是出现 vLLM、PagedAttention、continuous batching、FlashAttention、量化。

第五步：SFT 只能模仿标准答案，不保证偏好、安全和推理质量，所以需要 DPO/PPO/GRPO 等对齐方法；但 reward 是代理目标，所以必须防 reward hacking、KL 失控和 entropy collapse。

最后：所有技术都要回到指标。看不懂 TTFT、TPOT、P99、loss、reward、KL、entropy，就无法证明优化真的有效。

零、先建立全局地图：大模型到底怎么从训练到上线

你可以先把大模型理解成一个“超大的函数”：输入一串文字，模型把文字拆成 token，经过很多层 Transformer 计算，输出下一个 token 的概率。训练是在调整这个函数里的参数；推理是在使用训练好的函数生成答案；部署是在让这个函数稳定、便宜、快速地服务很多用户。

数据准备：收集文本、代码、问答、偏好数据，清洗去重，切成 token。数据质量决定模型上限。
预训练：让模型做“预测下一个 token”的任务，学语言、知识和模式。这里最吃算力和数据。
SFT 微调：用高质量指令数据教模型按人类指令回答，比如问答、代码、总结、推理格式。
对齐训练：用偏好数据、奖励模型、DPO/PPO/GRPO 等方法，让模型更符合人类偏好、安全和业务目标。
推理部署：把模型放到 GPU 服务上，对外提供 API，同时优化延迟、吞吐、显存、稳定性和成本。
监控迭代：上线后看 P99、错误率、成本、用户反馈、幻觉率、成功率，再继续调模型和系统。

小白类比：训练像“长期学习做题方法”，SFT 像“看标准答案学答题格式”，RL 对齐像“老师按偏好打分后继续改答题习惯”，推理部署像“考试时又快又稳地答题给很多人看”。

一、小白必懂词典：先把名词翻译成人话

模型 Model

一套可以把输入映射成输出的参数系统。LLM 的输入是 token 序列，输出通常是下一个 token 的概率。

参数 Parameter

模型内部可学习的数字。训练就是不断调整这些数字，让模型预测更准、回答更好。

Token

模型处理文字的基本单位，可能是一个字、一个词、一个符号或词的一部分。成本和速度通常按 token 算。

Embedding

把 token 变成向量。模型不能直接理解文字，只能处理数字向量。

上下文 Context

模型当前能看到的输入和历史对话。上下文越长，能放的信息越多，但成本和噪声也更高。

Logits

模型在 softmax 前输出的原始分数。每个候选 token 都有一个分数。

Softmax

把一堆分数变成概率分布。分数越高的 token，被选中的概率越大。

Loss

模型“错得有多离谱”的数字。训练目标通常是让 loss 下降，但业务效果不能只看 loss。

梯度 Gradient

告诉参数应该往哪个方向改，才能让 loss 变小。反向传播就是计算梯度的过程。

优化器 Optimizer

根据梯度更新参数的算法，比如 AdamW。它决定每一步怎么改、改多大。

Batch

一次送进模型处理的一组样本或请求。batch 大通常吞吐高，但显存占用也高。

GPU

适合做大规模矩阵运算的硬件。大模型训练和推理依赖 GPU 的并行计算能力。

显存 VRAM

GPU 上的内存，用来放模型参数、KV Cache、激活、梯度等。显存不够模型就跑不起来。

吞吐 Throughput

单位时间处理多少 token 或请求。推理服务更常看 tokens/s，而不只是 QPS。

延迟 Latency

用户等多久拿到结果。LLM 常看首 token 延迟 TTFT 和每 token 延迟 TPOT。

Checkpoint

训练中保存的模型状态。训练中断后可以恢复，也用于版本管理和回滚。

Attention

让每个 token 决定该关注上下文里的哪些 token。它是 Transformer 的核心。

KV Cache

推理时缓存历史 token 的 Key/Value，避免每生成一个 token 都重复计算全部历史。

Reward

RL 中给模型输出打的分。分数设计不好，模型会学会钻空子。

KL

衡量新模型和参考模型输出分布差多远。对齐训练用它防止模型跑偏。

Entropy

输出分布的“不确定性”。太低说明模型过早变得死板，太高说明输出可能太散。

小白先记住一句话

训练关注“怎么把参数学好”，推理关注“怎么把答案生成得又快又省”，分布式关注“单卡放不下或跑太慢时怎么拆到多卡”，RL 对齐关注“怎么让模型更符合人类和业务偏好”。

二、核心主题完整讲解：按教材方式把每个重点讲透

这一部分是主学习区。建议先顺序读，不要跳着背名词。每个主题都按“问题从哪来 -> 为什么朴素方案不够 -> 核心原理 -> 工程代价 -> 面试表达”来组织。

1. Transformer 完整链路：从一句话到下一个 token

先读懂这一句话：Transformer 的本质是把文字变成向量，再让每个 token 通过 attention 从上下文里取信息，经过多层加工后输出下一个 token 的概率分布。

为什么会出现这个问题

语言模型要解决的问题并不是“记住一段话”，而是“在给定前文的条件下，判断下一个 token 最可能是什么”。早期的 RNN 按顺序读 token，天然符合时间序列，但长距离依赖弱，而且很难并行。CNN 可以并行，但固定窗口对远距离关系不够灵活。Transformer 的出现，是为了同时解决两个矛盾：既要让任意两个 token 能直接交互，又要适合 GPU 上的大规模矩阵并行。

完整计算流程

第一步是 tokenizer，把文本切成 token id。模型不直接处理汉字或英文单词，而是处理整数 id。第二步是 embedding，把 token id 查表变成向量。例如每个 token 变成一个 d_model 维向量。第三步进入多层 Transformer block，每层通常包含 attention、MLP、残差连接和归一化。第四步通过输出投影把最后一层隐状态映射回词表大小的 logits。第五步对 logits 做 softmax 得到概率，再按 greedy、top-k、top-p 或 temperature 采样选出下一个 token。

训练目标：P(x_1...x_T)=Π_t P(x_t|x_<t)，也就是整段文本的概率被拆成逐 token 条件概率。训练时最小化 -log P(真实下一个 token)。

Attention 为什么是核心

Attention 解决的是“当前 token 应该看前文的哪些信息”。例如“张三把书给了李四，因为他明天要考试”，模型要判断“他”指谁，必须比较前文多个实体和语义关系。Q/K/V 可以这样理解：Q 是当前 token 发出的查询，K 是每个 token 暴露的索引，V 是真正被取走的信息。Q 和 K 点积越大，说明越相关，对应 V 的权重越高。

Attention 公式：Attention(Q,K,V)=softmax(QK^T/sqrt(d_k))V。QK^T 计算相关性，softmax 变成权重，最后对 V 加权求和。

朴素方案为什么不够

如果没有 attention，模型只能靠固定窗口或递归隐状态传递信息，远距离关系容易丢。如果只有单头 attention，模型只有一种“关注方式”，表达力不够。多头注意力让不同 head 学不同关系：有的关注局部词法，有的关注实体指代，有的关注格式结构，有的关注长距离依赖。

代价是什么

attention 的代价来自两两交互。序列长度为 n 时，注意力矩阵是 n × n，所以标准 attention 的计算和显存都近似 O(n^2)。这就是长上下文昂贵的根源。后面的 FlashAttention、KV Cache、PagedAttention、上下文压缩，本质都在围绕这个代价做工程优化。

面试能答到这个程度就够了：Transformer 用 attention 建模 token 间关系，用 MLP 做逐位置非线性加工，用残差和归一化保证深层训练稳定。它强在并行和可扩展，但代价是长序列下 attention 的 O(n^2) 成本。

2. RoPE、多头注意力、MQA/GQA：从表达能力到推理成本

先读懂这一句话：多头注意力提升表达能力，RoPE 让模型知道 token 的相对位置，MQA/GQA 则是在推理阶段为了减少 KV Cache 成本做的取舍。

为什么需要位置编码

Attention 本身对顺序不敏感。如果输入 token 只是一个集合，模型无法知道“我喜欢你”和“你喜欢我”的区别。因此必须把位置信息注入模型。绝对位置编码给每个位置一个固定向量，但长上下文外推时不够自然；RoPE 用旋转的方式把位置注入 Q/K，使点积天然包含相对距离。

RoPE 推导直觉：<R_m q, R_n k> = <q, R_{n-m} k>。位置 m 和 n 的绝对旋转，在点积里会转化成相对距离 n-m，所以模型更容易学习“相隔多远”的关系。

多头注意力为什么不是越多越好

多头的价值在于把表示空间拆成多个子空间，让模型并行学习不同关系。但 head 数增加会影响每个 head 的维度、计算布局和 KV Cache 大小。训练时多头提高表达力，推理时每层每个 token 都要缓存 K/V，head 数越多，KV Cache 越大，显存带宽压力越高。

MQA/GQA 从哪里来

标准 MHA 中，每个 query head 都有自己的 K/V head。推理时，历史 token 的 K/V 要被缓存。如果模型层数多、上下文长、并发高，KV Cache 会迅速变成主要显存瓶颈。MQA 让所有 query head 共享一组 K/V，极大减少 KV Cache；GQA 则把 query head 分组，每组共享一组 K/V，在质量和成本之间折中。

KV Cache 估算：KV bytes ≈ batch × seq_len × layers × 2 × kv_heads × head_dim × bytes。MQA/GQA 直接减少 kv_heads，所以能显著省显存。

常见误区

RoPE 不等于无限长上下文。它让位置表达更适合外推，但训练长度、数据分布、注意力稀释和噪声仍会限制长上下文能力。MQA/GQA 也不是纯收益，它减少 K/V 表达多样性，极端压缩可能影响质量。因此工程上常选 GQA，因为它比 MQA 更稳，又比 MHA 更省。

面试能答到这个程度就够了：RoPE 解决位置关系，多头解决表达多样性，GQA/MQA 解决推理阶段 KV Cache 太大的问题。三者不是孤立知识点，而是从“模型要理解顺序和关系”一路推到“上线时要控制显存和吞吐成本”。

3. 推理服务完整链路：为什么 LLM 上线后会慢、贵、难稳定

先读懂这一句话：LLM 推理不是一次函数调用生成整段答案，而是先读完整 prompt，再逐 token 循环生成；慢和贵都来自这个自回归过程。

为什么会出现这个问题

传统分类模型输入一张图或一段文本，通常一次 forward 就给结果。LLM 不一样，生成一句话需要很多次 forward。第一个阶段是 prefill：模型处理用户输入的全部 prompt，建立上下文状态；第二个阶段是 decode：模型每次只生成一个 token，把新 token 接回上下文，再继续生成下一个 token。输出越长，decode 次数越多。

朴素方案为什么不够

最朴素的做法是每来一个请求就单独跑模型。这会让 GPU 经常吃不满，因为 decode 每步只处理一个新 token，矩阵规模小，并行度不足。于是需要 batching，把多个请求合在一起跑。但 LLM 请求长度差异巨大：有人问一句话，有人贴一篇论文；有人生成 20 个 token，有人生成 2000 个 token。普通 static batching 会被最长请求拖住，短请求结束后 GPU 槽位不能及时复用。

核心指标怎么对应问题

TTFT 衡量用户多久看到第一个 token，主要受排队、prefill、调度影响。TPOT 衡量后续每个 token 多久生成，主要受 decode、KV Cache、batch 调度和显存带宽影响。P99 衡量长尾体验，常被超长请求、队列阻塞或显存抢占拉高。tokens/s 衡量吞吐，比 QPS 更适合 LLM，因为同样一个请求可能有完全不同的 token 数。

完整因果链：自回归逐 token 生成 -> decode 阶段并行度不足 -> 需要 batching -> 请求长短不一导致 static batching 低效 -> continuous batching 和 vLLM 这类推理引擎出现。

工程实现怎么落地

生产推理服务通常不只是一个模型进程，而是一套服务系统：入口层做鉴权、限流和队列；调度器决定哪些请求进入 batch；推理引擎管理模型权重、KV Cache、prefill/decode；监控系统记录 TTFT、TPOT、P95/P99、显存水位、GPU 利用率、错误率和超时率。优化时不能只盯一个指标，否则容易牺牲用户体验换平均吞吐。

面试能答到这个程度就够了：我会先拆 prefill 和 decode，再用 TTFT/TPOT/P99 定位瓶颈。如果 TTFT 高，优先看排队、prompt 长度、prefill；如果 TPOT 高，优先看 KV Cache、decode batch、显存带宽和调度策略。

4. KV Cache、PagedAttention、vLLM、SGLang：从重复计算到系统调度

先读懂这一句话：KV Cache 解决重复计算，但带来显存压力；PagedAttention 解决 KV Cache 管理浪费；vLLM 把这些能力做成高吞吐推理引擎；SGLang 更强调复杂 LLM 程序的编排和执行。

KV Cache 为什么出现

自回归生成第 t 个 token 时，前面 1...t-1 个 token 的 K/V 已经算过，而且不会因为新 token 改变。没有 KV Cache，每生成一个 token 都要重新处理完整前缀，成本非常高。有了 KV Cache，每一步只计算新增 token 的 Q/K/V，然后把新增 K/V 追加到缓存里。

显存公式：KV bytes ≈ batch × seq_len × layers × 2 × kv_heads × head_dim × bytes。这说明上下文越长、并发越高、层数越多，KV Cache 越容易成为显存瓶颈。

PagedAttention 解决什么

传统 KV Cache 管理常常要求为每个请求预留连续显存。问题是 LLM 请求长度不可预测：如果预留太少，生成到一半不够用；预留太多，又浪费显存。请求结束时间也不同，会产生碎片。PagedAttention 借鉴操作系统分页，把每个请求的 KV Cache 切成固定大小 block，逻辑 block 通过 block table 映射到物理 block，不要求连续存储。

关键概念：logical block 表示请求视角中的 token 块；physical block 表示真实显存中的 KV 块；block table 记录“这个请求的第几个逻辑块在哪个物理块”。这样可以按需分配、复用、回收，减少碎片和过度预留。

vLLM 为什么吞吐高

vLLM 的核心不是“能加载模型”，而是把 PagedAttention、continuous batching、调度策略、KV Cache 管理做成推理服务引擎。continuous batching 是 iteration-level scheduling：每个 decode step 后，完成的请求退出，新的请求补进来。这样 GPU 不必等一整批请求全部结束，尤其适合输出长度差异大的场景。

SGLang 放在哪里理解

vLLM 更偏通用高吞吐 serving，SGLang 更偏复杂 LLM 程序执行。例如一个 Agent 任务可能包含多轮推理、分支采样、工具调用、结构化输出、共享前缀和缓存复用。SGLang 的价值是让这些复杂流程不只是业务代码串行调用模型，而是由运行时和调度器进行更系统的执行优化。

常见误区

PagedAttention 不会改变 attention 的数学复杂度，也不会让模型质量变好。它解决的是系统层的 KV Cache 管理问题。continuous batching 也不保证 P99 一定变好，如果长请求无限制进入队列，仍然可能拖慢短请求。因此生产上还要配合最大长度限制、优先级、超时取消、长度分桶和限流。

面试能答到这个程度就够了：KV Cache 是计算优化，PagedAttention 是显存管理优化，continuous batching 是调度优化，vLLM 是把这些组合起来的推理引擎，SGLang 则更适合复杂 LLM workflow。

5. FlashAttention 和量化：从算子 IO 到模型压缩

先读懂这一句话：FlashAttention 解决 attention 中间矩阵读写太重的问题，量化解决权重和计算带宽太贵的问题，二者都是不改变业务接口的底层效率优化。

FlashAttention 为什么出现

标准 attention 会计算 QK^T，形成一个 n × n 注意力矩阵。长序列下这个矩阵非常大，不只是计算贵，更重要的是中间结果要频繁在 HBM 和计算单元之间读写。GPU 很多时候不是算不动，而是数据搬运太慢。FlashAttention 的核心思想是 IO-aware：把 Q/K/V 分块搬到更快的片上存储里，分块计算，并用 online softmax 维护数值稳定，不完整物化巨大的注意力矩阵。

online softmax 直觉：softmax 需要全局最大值和归一化分母。FlashAttention 分块处理时，会逐块更新当前最大值和分母，使最终结果和标准 attention 等价，但避免保存完整 n × n 矩阵。

量化为什么出现

模型权重通常用 FP16/BF16 存储。模型越大，显存越大，加载越慢，推理时访存带宽压力也越高。量化把权重压到 INT8、INT4 等低比特格式，目标是用更小存储和更低带宽换取尽可能接近原模型的输出。它特别适合显存受限或需要降低服务成本的场景。

GPTQ 和 AWQ 的区别

GPTQ 更强调基于校准数据和近似二阶信息做误差补偿，目标是让量化后的层输出尽量接近原始输出。AWQ 的观察是：不是所有权重通道同等重要，少数激活敏感通道对输出影响更大，因此通过缩放和保护关键通道减少质量损失。两者都属于部署前的离线权重量化思路。

量化目标：min ||WX - W_qX||，其中 W 是原始权重，W_q 是量化权重，X 是校准数据激活。关键不是让权重数字本身最接近，而是让层输出尽量接近。

上线评估怎么做

量化后不能只看显存下降。必须看业务准确率、格式遵循、长推理稳定性、拒答率、幻觉率、P99、吞吐和回滚成本。INT4 不一定比 FP16 快，因为反量化 kernel、硬件支持、batch 大小都会影响速度。高精度推理、数学推理或安全敏感任务要谨慎量化。

面试能答到这个程度就够了：FlashAttention 是 attention 算子的 IO 优化，不改变模型语义；量化是权重/计算表示压缩，降低显存和带宽，但要评估质量损失和 kernel 性能。

6. 分布式训练完整讲解：DP、TP、PP、ZeRO、FSDP 到底在拆什么

先读懂这一句话：分布式训练不是简单“多几张卡一起跑”，而是分别拆数据、拆矩阵、拆层、拆训练状态，用通信换显存和吞吐。

为什么单卡不够

训练显存不只是模型参数。以 AdamW 为例，除了参数，还要保存梯度、一阶矩、二阶矩、激活值、临时 buffer，有时还有 FP32 master weights。推理时主要放权重和 KV Cache，训练时还要为反向传播保留中间激活，所以同一个模型训练显存远大于推理显存。

训练显存：memory ≈ parameters + gradients + optimizer states + activations + buffers。如果参数量继续变大，单卡首先会在参数/状态/激活其中一项上爆掉。

DP：复制模型，拆数据

数据并行最直观：每张 GPU 放一份完整模型，处理不同 mini-batch，反向传播后同步梯度。它适合模型单卡能放下、想提高吞吐的场景。问题是每张卡都复制完整参数、梯度和优化器状态，模型大到一定程度后，复制状态本身就不可接受。

TP：切一层里的矩阵

张量并行解决的是“单层太宽”。Transformer 里的 attention projection、MLP projection 都是大矩阵乘法。TP 把矩阵按列或按行切到多卡上，每张卡算一部分，再通过 all-reduce、all-gather 等通信组合结果。TP 通信频繁，因此最好放在同机 NVLink/NVSwitch 这类高速互联内。

矩阵切分：Y=XA。列并行把 A 按输出维切分，每卡得到部分 Y；行并行把输入维切分，每卡算部分乘积，再 all-reduce 求和。

PP：切不同层

流水线并行解决的是“模型太深，整模型放不下”。把前几层放 GPU0，中间几层放 GPU1，后几层放 GPU2。为了避免只有一张卡在工作，batch 会切成多个 micro-batch，让不同 stage 同时处理不同 micro-batch。代价是 pipeline bubble：流水线开头和结尾总会有空转，stage 切分不均也会导致慢 stage 拖住所有人。

ZeRO/FSDP：切训练状态

ZeRO 和 FSDP 解决的是 DP 状态冗余。ZeRO-1 切优化器状态，ZeRO-2 切优化器状态和梯度，ZeRO-3 连参数也切。FSDP 是 PyTorch 生态里的全分片数据并行方案，forward 前 all-gather 当前模块需要的完整参数，计算后释放，backward 再 reduce-scatter 梯度。它们用更多通信换更低显存。

混合并行怎么想

真实大模型训练往往不是单选题。可以用 TP 解决单层矩阵太大，用 PP 解决层数太深，用 DP/FSDP 扩吞吐和切状态。比如 64 卡可以组织成 TP=4、PP=4、DP=4。调参时要看 GPU 利用率、tokens/s、MFU、通信耗时、stage idle、显存水位和 dataloader 等待。

面试能答到这个程度就够了：DP 拆数据但复制模型；TP 拆层内矩阵，通信频繁；PP 拆层，有 pipeline bubble；ZeRO/FSDP 拆参数/梯度/优化器状态。混合并行的目标是显存放得下、通信不过载、每张卡都有活干。

7. Scaling law 和 MoE：为什么变大有效，为什么稀疏模型不是免费午餐

先读懂这一句话：Scaling law 解释了参数、数据和算力增加通常会降低 loss；MoE 试图用稀疏激活扩大总容量，但把难题转移到了路由、负载均衡和通信上。

Scaling law 从哪里来

经验上，语言模型的 loss 会随着参数量、训练 token 数和计算量增加而可预测下降。这不是说“越大一定越好”，而是在数据质量、训练目标和优化稳定的前提下，规模扩展通常带来更强的拟合和泛化能力。Chinchilla 一类结论提醒我们：模型参数和训练 token 要匹配，参数很大但训练数据不足，会浪费算力；数据很多但模型太小，也无法充分吸收。

经验形式：Loss(N,D) ≈ A/N^α + B/D^β + E。N 是参数量，D 是 token 数，E 是不可约误差。它不是严格物理定律，而是工程决策工具。

为什么 dense 模型成本高

Dense Transformer 每个 token 都会经过所有层、所有参数中的对应计算路径。模型越大，每个 token 激活的计算也越大。推理时这意味着更高延迟和成本；训练时意味着更高 FLOPs 和显存。于是人们希望增加总参数容量，但不让每个 token 都激活所有参数。

MoE 的核心思想

MoE 把普通 FFN 替换成多个 expert，每个 token 只路由到 top-k 个 expert。这样总参数量可以很大，但单 token 只激活一小部分参数。router 根据 token 表示计算每个 expert 的概率，选择 top-k expert，再把 expert 输出加权合并。

MoE 路由：p=softmax(W_r x)，y=Σ_{i in top-k} p_i E_i(x)。这里 E_i 是第 i 个 expert。

MoE 的工程代价

MoE 最大问题是负载均衡和通信。如果 router 总把 token 分给少数 expert，这些 expert 会过载，其他 expert 学不到东西。训练时还会出现跨卡 all-to-all 通信，因为 token 可能被路由到不同 GPU 上的 expert。推理时，如果 batch 很小或路由很分散，MoE 的硬件利用率可能不如 dense 模型。

长上下文和 scaling 的关系

长上下文并不是简单把窗口拉大。窗口越长，token 成本越高，注意力噪声越多，有效信息密度可能下降。实践里常结合 RAG、重排、摘要压缩、结构化上下文、引用校验来提高有效 token 比例。大模型能力、长上下文能力和检索系统能力需要一起设计。

面试能答到这个程度就够了：Scaling law 帮助决定参数、数据和算力怎么配；MoE 用稀疏激活扩大容量，但带来路由、负载均衡、all-to-all 通信和推理部署复杂度。

8. RL 对齐完整讲解：从 SFT 到 PPO、GRPO、DPO 和新一代推理优化算法

先读懂这一句话：SFT 让模型学会模仿答案，RL/偏好优化让模型更偏向“人类或业务真正想要的答案”，但 reward 只是代理目标，所以稳定性和评估同样重要。

为什么 SFT 不够

SFT 数据通常是 prompt 和标准回答。它能教模型回答格式、任务边界和基本行为，但它主要在模仿数据分布。现实中同一个问题可能有多个答案，哪个更有帮助、更安全、更简洁、更符合业务目标，不一定能靠 SFT 单独学出来。于是需要偏好数据：给同一 prompt 的多个回答排序，或给回答打分。

Reward model 和规则奖励

Reward 可以来自人工偏好训练出的 reward model，也可以来自可验证规则。例如数学题答案正确给 1 分，格式正确加 0.1，过长扣分，违反安全策略扣分。关键是 reward 必须尽量接近真实目标。如果 reward 只奖励“看起来有推理步骤”，模型可能学会堆步骤而不保证正确。

策略优化直觉：∇J(θ)=E[∇logπ_θ(a|s)A]。某个输出相对更好，advantage 为正，就提高它的概率；相对更差，就降低概率。

PPO 为什么强调“不要更新太猛”

如果只按 reward 最大化，模型可能快速偏离原来的语言能力，出现格式怪异、胡编、讨好 reward model 的行为。PPO 用概率比 r_t 和 clipping 限制新旧策略差异，让模型小步更新。LLM 场景里通常还加 KL penalty，约束 policy 不要离 reference model 太远。

PPO：L=E[min(rA, clip(r,1-ε,1+ε)A)]。这不是为了让模型不学习，而是为了让学习不要一步跑崩。

GRPO 为什么适合推理任务

推理任务常能自动验证答案，比如数学、代码测试、格式校验。同一题可以采样多条回答，比较它们的相对奖励。GRPO 用组内均值和方差归一化 advantage，减少不同题目难度不同导致的 reward 尺度差异，同时减少对单独 value model 的依赖。

DPO 为什么工程简单

DPO 不显式训练 reward model，也不走复杂 rollout + critic 流程，而是直接用 chosen/rejected 偏好对优化模型，让模型提高 chosen 相对 rejected 的概率。它稳定、简单、成本低，适合先做 baseline；但如果任务需要在线探索、复杂规则奖励或多步环境反馈，PPO/GRPO 类方法仍有价值。

更新的偏好优化和推理 RL 方法怎么看

近两年很多算法都在围绕一个目标改进：减少 PPO 的复杂度，或者让推理任务的 RL 更稳定。ORPO 把 SFT 和偏好优化揉进一个目标，避免额外参考模型和复杂 RL 流程；SimPO 用更简单的偏好目标和长度归一化思想，降低 DPO 类方法的实现负担；KTO 不要求严格的 chosen/rejected 成对数据，而是利用“好/坏”反馈，更接近真实产品反馈；RLOO 和 ReMax 试图用更轻量的 baseline 减少方差，降低 value model/critic 的成本；DAPO、Dr.GRPO 等则更多面向可验证推理任务，关注 GRPO 在长度偏置、组内方差、负样本更新、训练稳定性上的问题。

这些算法不是互相完全替代，而是在不同数据形态和工程约束下做取舍：如果只有偏好对，DPO/SimPO/ORPO 更直接；如果只有正负反馈，KTO 更自然；如果有可验证答案并能同题多采样，GRPO/DAPO/Dr.GRPO 更合适；如果想保留 RL rollout 但降低 critic 成本，可以看 RLOO/ReMax。

reward hacking 和 entropy collapse

reward hacking 是模型学会钻 reward 的漏洞，而不是真正变好。例如奖励格式完整，模型就输出固定模板；奖励详细解释，模型就变啰嗦；奖励模型偏好自信语气，模型就更会胡编。entropy collapse 是输出分布过早变尖，模型变得死板、缺乏探索，常伴随多样性下降和模式化回答。

面试能答到这个程度就够了：我会先说 SFT 的局限，再说 reward 如何定义，再按数据形态选算法：偏好对用 DPO/SimPO/ORPO，正负反馈可看 KTO，可验证推理任务用 GRPO/DAPO/Dr.GRPO，复杂在线探索才考虑 PPO/RLOO/ReMax。最后补稳定性：KL、entropy、长度、人工抽样、holdout 回归集一起看。

9. 指标排障完整讲解：如何从曲线反推问题原因

先读懂这一句话：指标不是为了展示成果，而是为了定位因果。看到曲线异常时，要先拆阶段，再拆资源，再拆数据和策略。

推理排障：先拆 TTFT 和 TPOT

用户说“慢”时，先不要直接上优化。要看慢在首 token 还是后续 token。TTFT 高通常说明排队、prefill、prompt 长度、冷启动或调度有问题。TPOT 高通常说明 decode、KV Cache、显存带宽、batch 参数或长短请求混排有问题。P99 高而平均值正常，说明少数长尾请求破坏体验，要看超长 prompt、超长输出、队列阻塞、显存抢占或限流策略。

训练排障：先拆数据、计算、通信、调度

训练吞吐低不一定是 GPU 差。可能是 dataloader 没喂上，可能是 all-reduce/all-gather 等通信太重，可能是 pipeline bubble，可能是 batch 太小导致矩阵规模不够，可能是 checkpoint 太频繁。loss NaN 则优先查学习率、混精溢出、脏数据、梯度爆炸、归一化和 reward scale。

RL 排障：reward 不是最终答案

RL 对齐最容易出现“reward 曲线很好看，但模型变差”。这时要拆 reward 子项，看是不是长度、格式、模板、裁判偏好某一项主导；看 KL 是否突然升高，说明模型偏离参考；看 entropy 是否快速下降，说明策略变死板；看 response length 是否异常增长，说明可能通过啰嗦拿分。

排障顺序：现象 -> 阶段拆解 -> 指标定位 -> 样本抽查 -> 小规模复现实验 -> 调参或改 reward/系统策略 -> 回归集验证。

怎么证明修复有效

不能只说“我调了参数”。推理优化要给出 TTFT、TPOT、P99、tokens/s、错误率、成本变化；训练优化要给出 tokens/s、MFU、显存水位、loss 稳定性；RL 优化要给出 reward、KL、entropy、任务成功率、人工抽样、长度变化和 holdout 表现。最好还能说明副作用，比如吞吐上升是否牺牲了 P99，量化是否牺牲了准确率。

面试能答到这个程度就够了：任何优化都按“问题背景 -> 指标定位 -> 原因假设 -> 方案 -> 验证 -> 副作用”讲。能讲副作用和失败复盘，比只讲技术名词更可信。

三、数学和训练目标最小必备：后面公式都从这里来

1. next-token prediction：大模型预训练到底在学什么？

给定前面的 token 序列 x_1, x_2, ..., x_{t-1}，模型要预测下一个 token x_t。所以语言模型学的是条件概率：

公式：P(x_1, ..., x_T) = Π_t P(x_t | x_1, ..., x_{t-1})

推导直觉：一整段文本出现的概率，可以拆成“第 1 个词出现的概率 × 第 2 个词在前文条件下出现的概率 × ...”。训练时不断让真实下一个 token 的概率变高。

2. softmax：为什么 logits 能变成概率？

模型最后输出一组 logits，词表里每个 token 一个分数。softmax 把任意实数分数变成总和为 1 的概率分布：

公式：p_i = exp(z_i) / Σ_j exp(z_j)

原理：exp 会放大高分 token 的优势；分母做归一化，让所有 token 概率加起来等于 1。温度采样里的 temperature 本质是在缩放 logits，温度低更确定，温度高更多样。

3. 交叉熵 loss：为什么它能衡量预测错得多不多？

单 token 公式：L = -log p(y)，其中 y 是真实 token，p(y) 是模型给真实 token 的概率。

推导直觉：如果模型给真实 token 概率是 0.9，-log(0.9) 很小；如果只给 0.01，-log(0.01) 很大。训练就是让真实 token 的概率越来越高。

工程意义：loss 下降说明模型更会拟合训练/验证数据，但不等于线上回答一定更好。对齐、安全、事实性、格式遵循都需要额外评估。

4. 梯度下降和 AdamW：参数怎么被更新？

梯度下降：θ_{new} = θ - η ∇_θ L

解释：θ 是参数，η 是学习率，∇_θ L 是 loss 对参数的梯度。梯度指向 loss 上升最快方向，所以减去梯度就是往 loss 下降方向走。

AdamW 直觉：AdamW 会维护梯度的一阶矩和二阶矩，相当于给每个参数自适应学习率；W 表示 decoupled weight decay，用权重衰减抑制参数过大，改善泛化。

5. 困惑度 perplexity：和 loss 什么关系？

公式：PPL = exp(cross_entropy)

直觉：PPL 可以粗略理解成“模型平均每一步有多少个同样可能的选择”。PPL 越低，说明模型对下一个 token 越确定。但和业务效果一样，PPL 不是唯一指标。

四、Transformer 从零理解：文字如何变成回答

前因后果：传统序列模型要按时间步处理，长距离依赖弱、并行效率低 -> attention 让任意 token 可以直接看任意 token -> Transformer 适合 GPU 上的大矩阵并行 -> 但全局两两交互带来 O(n^2) 成本，所以长上下文和推理优化会成为后续问题。

读完本章要能回答：模型为什么要把文字变成向量？Q/K/V 分别干什么？为什么 attention 强但长上下文贵？为什么 RoPE 能补位置信息？

1. 一次回答在模型内部发生了什么？

第一步：输入文字被 tokenizer 切成 token，例如“你好世界”可能被切成几个数字 id。

第二步：每个 token id 查表变成 embedding 向量。向量不是语义本身，但能承载语义相似性。

第三步：向量通过很多层 Transformer block。每层主要做两件事：attention 负责看上下文，MLP 负责加工特征。

第四步：最后输出 logits，经 softmax 变成下一个 token 的概率，然后采样或贪心选择一个 token。

第五步：新 token 接到上下文后继续重复，直到生成结束符或达到最大长度。

Attention 是什么

一句话：让当前 token 从上下文里“找重点”。比如回答“他是谁”时，模型需要回看前文里“他”指代的名字。

MLP 是什么

一句话：对每个位置的特征做非线性加工。很多知识和模式会体现在 MLP 参数中。

残差和归一化

残差让信息不容易在深层网络里丢失；LayerNorm/RMSNorm 让数值更稳定，训练不容易崩。

2. Q、K、V 怎么理解？

类比：Query 像“我要找什么”，Key 像“我有什么标签”，Value 像“真正要拿走的信息”。当前 token 用 Q 去和所有 token 的 K 匹配，匹配越高，就从对应 V 里拿更多信息。

为什么要多头：一个头可能关注语法，一个头关注实体，一个头关注位置。多头让模型能同时从多个角度理解上下文。

为什么需要 RoPE：如果没有位置信息，模型只看到一堆 token，不知道谁在前谁在后。RoPE 用旋转方式把相对位置注入 Q/K，让模型知道距离关系。

3. 专业版：Attention 的公式、维度和复杂度

核心公式：Attention(Q,K,V) = softmax(QK^T / sqrt(d_k))V

维度：若序列长度为 n，单头维度为 d_k，则 Q,K,V 的形状通常是 n × d_k；QK^T 得到 n × n 注意力分数矩阵，表示每个 token 对每个 token 的关注程度。

为什么除以 sqrt(d_k)：点积维度越大，数值方差越大，softmax 容易饱和，梯度变小。除以 sqrt(d_k) 是为了稳定分数尺度。

复杂度：标准 self-attention 的计算和显存与序列长度近似成 O(n^2)，因为要形成每个 token 两两交互的注意力矩阵。长上下文贵，根源就在这里。

4. 专业版：RoPE 为什么能表达相对位置？

RoPE 会把位置 m 对应的旋转作用到 q_m，把位置 n 对应的旋转作用到 k_n。旋转后的点积会天然依赖 m-n，也就是相对距离。

推导直觉：<R_m q, R_n k> = <q, R_{n-m} k>。两个位置的绝对旋转可以合并成相对旋转，所以 attention 分数携带相对位置信息。

工程意义：RoPE 对长度外推更友好，但训练时没见过的超长位置仍可能退化，所以长上下文还要配合位置插值、NTK scaling、YaRN、数据扩长和检索压缩。

五、推理优化从零理解：为什么回答会慢，怎么变快

前因后果：LLM 生成答案必须逐 token 解码 -> 每一步都要依赖历史上下文 -> KV Cache 避免重复算历史，但显存占用暴涨 -> vLLM/PagedAttention 管 KV，continuous batching 管调度，FlashAttention 管 attention IO，量化管显存和带宽。

读完本章要能回答：首 token 慢和输出慢为什么不是一回事？为什么 KV Cache 既提速又吃显存？为什么请求长短不一会影响 GPU 利用率？

1. 推理是什么？

推理就是使用训练好的模型生成答案。用户输入 prompt 后，模型不会一次性吐出整段话，而是一个 token 一个 token 地生成。每生成一个 token，都要把它接回上下文，再预测下一个 token。

例子：用户问“什么是 KV Cache？”模型可能先生成“KV”，再生成“ Cache”，再生成“ 是”，一直循环直到完整回答结束。

2. 为什么分 prefill 和 decode？

prefill：处理用户已经给出的整段 prompt，计算所有输入 token 的中间状态。它像“读题”，题目越长，读题越慢。

decode：开始逐 token 生成答案。它像“一个字一个字写答案”，每一步都依赖前一步，所以并行性更差。

工程意义：首 token 慢通常和 prefill、排队有关；流式输出慢通常和 decode、KV Cache、batch 调度有关。

KV Cache

解决重复计算。历史 token 的 K/V 已经算过，缓存起来，下次只算新增 token。

PagedAttention

解决 KV Cache 显存碎片。像内存分页一样按块管理 KV，而不是要求连续大块显存。

Continuous Batching

解决 GPU 等待。请求完成就退出，新请求马上补进来，让 GPU 持续有活干。

量化

解决显存和带宽。把 FP16/BF16 权重压成 INT8/INT4，但可能损失质量。

FlashAttention

解决 attention 读写太重。它不改结果，主要减少中间矩阵的显存读写。

SGLang

解决复杂 LLM 程序编排。多轮、多分支、工具调用、结构化输出场景更有优势。

3. 小白怎么判断一个优化手段该不该用？

先问瓶颈在哪里。显存不够，考虑量化、GQA/MQA、KV 管理；吞吐不够，考虑 vLLM、continuous batching、batch 参数；首 token 慢，考虑 prompt 长度、排队、chunked prefill；质量下降，检查量化和上下文裁剪是否过度。

4. 专业版：prefill / decode 的复杂度差异

prefill：一次处理长度为 n 的 prompt，attention 需要看完整 n × n 关系，单请求计算量大，但矩阵乘法并行度高，GPU 容易吃满。

decode：每一步只新增 1 个 token，但要读历史所有 token 的 KV，单步 attention 近似 O(n)，连续生成 m 个 token 后总成本和上下文长度、输出长度都相关。

工程结论：TTFT 主要受 prefill、排队和调度影响；TPOT 主要受 decode 调度、KV Cache 读写、batch 形态和显存带宽影响。

六、分布式训练从零理解：为什么要把模型拆到多张卡

前因后果：训练要保存参数、梯度、优化器状态和激活 -> 单卡显存和算力不够 -> DP 提吞吐但复制状态，TP 切单层矩阵，PP 切层，ZeRO/FSDP 切训练状态 -> 大模型训练通常需要混合并行。

读完本章要能回答：为什么训练比推理更吃显存？TP、PP、ZeRO/FSDP 各自解决哪类瓶颈？为什么并行度不是越大越好？

1. 单卡为什么不够？

训练时 GPU 不只要放模型参数，还要放梯度、优化器状态、激活值和临时 buffer。推理可能只需要放模型和 KV Cache，但训练要保存更多中间信息，所以显存压力大得多。

直觉：推理像“拿已经学好的书答题”，训练像“边做题边记录每一步错在哪里，还要修改整本书”。需要保存的信息更多。

3. 小白先掌握 TP 和 PP 到什么程度？

TP：会解释“把同一层的大矩阵拆开算，再通信合并”。知道它适合单层很大，通信很频繁，最好放在同机高速互联内。

PP：会解释“把模型按层切成 stage，用 micro-batch 流水线跑”。知道它有空泡 bubble，stage 切不均会导致有的 GPU 等别人。

面试够用表达：我能根据显存、模型层数、单层矩阵大小和集群拓扑判断为什么用 TP/PP/ZeRO，而不是只背框架名。

4. 专业版：训练显存大概由什么组成？

粗略公式：训练显存 ≈ 参数 + 梯度 + 优化器状态 + 激活 + 临时 buffer

AdamW 场景：参数一份，梯度一份，一阶矩 m 一份，二阶矩 v 一份；如果还有 FP32 master weights，显存会继续增加。因此训练显存通常远大于推理显存。

activation checkpointing：它不保存全部中间激活，而是在 backward 时重算一部分，用更多计算换更少显存。

七、RL 对齐从零理解：让模型不只是会说，还要说得符合目标

前因后果：SFT 让模型模仿标准答案 -> 但“标准答案”不等于人类偏好或业务目标 -> reward 把偏好变成可优化信号 -> PPO/GRPO/DPO 优化偏好 -> reward 不完美会引出 reward hacking、KL 失控和熵崩溃。

读完本章要能回答：为什么 reward 不是越高越好？为什么要 KL 约束？为什么 GRPO 适合可验证推理任务？

1. 为什么 SFT 后还要对齐？

SFT 能让模型学会“按指令回答”的格式，但不一定知道哪种回答更好、更安全、更符合业务目标。对齐就是继续告诉模型：什么样的答案更值得被偏好。

例子：两个答案都语法正确，但一个更有帮助、引用更准确、格式更稳定。偏好学习和 RL 对齐就是让模型更常生成后者。

2. RL 里的几个角色

Policy

当前要训练的模型。它决定给定 prompt 时输出什么回答。

Reference Model

参考模型，通常是 SFT 模型。用来约束新模型别跑太远。

Reward Model / Rule

给回答打分的模型或规则。它告诉 policy 哪些输出更好。

KL Penalty

惩罚新模型偏离参考模型太多，防止为了高分乱学。

3. PPO、GRPO、GSPO 以及更新算法怎么系统理解？

先分清两条路线：一条是真正做 rollout 的 RL 路线，模型会采样回答、拿 reward、再更新策略，例如 PPO、GRPO、RLOO、ReMax、DAPO/Dr.GRPO；另一条是偏好优化路线，不一定显式 rollout，而是直接利用偏好数据优化模型，例如 DPO、IPO、KTO、ORPO、SimPO。

为什么会有这么多算法：PPO 稳但链路重 -> DPO 想去掉 reward model + critic + rollout -> GRPO 想利用同题多回答的相对比较 -> ORPO/SimPO/KTO 想降低偏好数据和训练流程成本 -> DAPO/Dr.GRPO 想解决长推理 RL 的稳定性和偏置问题。

PPO：经典 RLHF 主力算法。它有 policy、reference、reward model、value/critic，用 clipped objective 和 KL 控制更新幅度。优点是通用，能处理复杂 reward；缺点是训练链路重、显存成本高、调参难，容易出现 KL 失控、value loss 抖动、reward hacking。

GRPO：Group Relative Policy Optimization。同一个 prompt 采样多条回答，用组内 reward 均值/方差构造相对 advantage，减少对 value model 的依赖。它适合数学、代码、推理这种能自动判分、能同题多采样的任务；风险是 reward 噪声、组内样本质量和长度偏置会影响更新。

GSPO：可以按“序列级策略优化”理解，更关注整条回答的概率和质量，而不是只在 token 级别做局部更新。它的动机是长推理里单 token 概率噪声很大，序列级目标更贴近“这整条答案好不好”。如果面试没有要求公式，重点讲动机和适用场景即可。

DPO：Direct Preference Optimization。它直接用 chosen/rejected 偏好对优化相对概率，不显式训练 reward model，也不需要 PPO 式 rollout。优点是简单稳定、工程成本低；缺点是依赖偏好对质量，探索能力弱，不适合复杂在线反馈。

4. 小白最容易误解什么？

误解一：reward 越高模型越好。错，reward 只是代理目标，可能被模型钻空子。

误解二：loss 下降就能上线。错，还要看任务成功率、人工抽样、安全、长度、成本和回归集。

误解三：熵越低越好。错，熵太低说明模型变死板，可能探索不足、输出模式坍缩。

八、深挖推理优化：从 KV Cache 到 vLLM / SGLang

本章逻辑：先从用户体验指标出发，定位慢在 prefill 还是 decode；再从 decode 的重复计算推出 KV Cache；再从 KV Cache 的碎片和浪费推出 PagedAttention；再从请求动态到达和结束推出 continuous batching；最后根据瓶颈选择 FlashAttention、量化、SGLang 等方案。

Q1：大模型推理优化到底在优化什么？总纲

口语稿：推理优化不是单纯“跑得更快”，而是在 SLA 约束下平衡首 token 延迟、单 token 生成速度、吞吐、显存占用、稳定性和成本。

核心原理：自回归模型推理分成 prefill 和 decode。prefill 对整段 prompt 并行计算，主要吃算力；decode 每次生成一个 token，强依赖 KV Cache 和调度效率，常常更容易受显存带宽、批处理策略和请求长度分布影响。

项目落地：上线前先看请求长度分布、并发峰值、TTFT、TPOT、P95/P99、GPU 利用率、显存水位和队列长度。没有这些基线，讨论 vLLM、量化、FlashAttention 都容易变成堆名词。

从现象到方案：P99 高但 GPU 利用率不高 -> 先怀疑排队、batch 调度或长短请求混排 -> 引入 continuous batching、长度分桶、优先级队列；显存水位高 -> 再看 KV Cache、量化、GQA/MQA、PagedAttention。

追问应对：如果被问“优化顺序”，可以说先做指标和压测，再看瓶颈：显存不足优先量化/KV 管理，吞吐不足看 continuous batching，长上下文慢看 FlashAttention、上下文裁剪和 prefill 优化。

Q2：KV Cache 为什么能提速？代价是什么？高频

口语稿：自回归生成时，历史 token 的 Key/Value 不会随着新 token 改变，所以可以缓存每层历史 K/V。下一步只需要算新增 token 的 Q/K/V，再和历史 K/V 做注意力，避免重复计算整段上下文。

没有 KV Cache：每步近似重复处理完整前缀；有 KV Cache：每步只追加新 token 的 K/V，但注意力仍要读历史 K/V。

工程代价：KV Cache 会占用大量显存，且和 batch size、层数、隐藏维度、序列长度、KV 头数、精度直接相关。长上下文和高并发时，KV Cache 往往是显存瓶颈。

显存估算：KV bytes ≈ batch × seq_len × layers × 2(K,V) × kv_heads × head_dim × bytes_per_elem

推导直觉：每层都要存 K 和 V；每个 token 都有每个 KV head 的向量；精度越高单元素字节数越大。GQA/MQA 通过减少 kv_heads 直接省显存。

追问应对：如果问“为什么 GQA/MQA 有用”，答：它们减少 K/V 头数，直接降低 KV Cache 体积和显存带宽压力，但可能牺牲部分表达能力。

Q3：PagedAttention 的核心思想是什么？vLLM

口语稿：PagedAttention 把 KV Cache 管理做得像操作系统的虚拟内存分页：不要求每个请求拿到一整块连续显存，而是把 KV 按 block 存储，通过 block table 映射逻辑位置和物理块。

为什么重要：传统 KV Cache 容易因为变长请求产生显存碎片和预留浪费。PagedAttention 让显存按块分配、复用和回收，提升并发下的显存利用率。

block table 原理：逻辑上的 token 位置被映射到物理 KV block。请求 A 的第 0-15 个 token 可以在物理 block 7，请求 B 的第 0-15 个 token 可以在物理 block 2；调度器通过表查找，不要求连续显存。
从现象到方案：请求长度差异大 -> 连续大块 KV 预留浪费 -> 显存碎片导致可用显存下降 -> 按 block 管理 KV，并用 block table 做逻辑到物理映射。

项目落地：适合请求长度差异大、并发高、长上下文多的服务。上线要关注 block size、显存水位、抢占策略、swap/evict 行为和长请求对短请求的影响。

追问应对：PagedAttention 不是改变模型结构，也不是让注意力复杂度消失。它主要优化 KV Cache 的系统管理效率。

Q4：vLLM 为什么吞吐高？高频

口语稿：vLLM 的核心价值是 PagedAttention 加 continuous batching。前者提升 KV Cache 显存利用率，后者让不同请求在 token step 级别动态入批，减少 GPU 空转。

调度直觉：传统 static batching 要等一批请求凑齐，并且整批完成后才能处理下一批；continuous batching 可以让已经完成的请求退出，新请求补进来，特别适合输出长度不一致的 LLM 服务。

面试说法：我会把 vLLM 定位成推理服务引擎，不只是模型加载器。它解决的是高并发下的调度、KV 管理和吞吐成本问题。

从现象到方案：一批请求里有人很快结束、有人生成很长 -> static batching 会让 GPU 槽位被长请求拖住 -> iteration-level scheduling 让完成的请求退出、新请求补位 -> GPU 利用率和吞吐更稳。

追问应对：如果 P99 变差，要检查队列等待、长请求占用、batch token 数、max_num_seqs、max_num_batched_tokens、GPU 显存水位，而不是只看平均吞吐。

Q5：SGLang 和 vLLM 的区别怎么讲？系统选型

口语稿：vLLM 更偏通用高吞吐推理引擎，SGLang 更强调结构化生成程序、复杂推理流程、前后端协同调度和 KV Cache 复用。

核心能力：SGLang 常用于多轮、多分支、工具调用、agentic workflow、JSON/约束输出等场景。它通过运行时和调度器优化，让复杂 LLM 程序不只是串行调用模型。

选型话术：如果只是标准 chat completion，高吞吐服务优先考虑 vLLM；如果业务里有复杂提示编排、多阶段推理、可复用前缀、并发分支，SGLang 的编程模型更有吸引力。

追问应对：不要说二者谁完全替代谁。更准确的是看调用模式、模型支持、部署生态、团队熟悉度和压测结果。

Q6：FlashAttention 原理怎么讲清楚？算子

口语稿：FlashAttention 不改变注意力数学结果，改变的是执行方式。它通过分块计算和在线 softmax，减少注意力矩阵在 HBM 中的读写和物化，从而提升速度、降低显存。

核心瓶颈：标准 attention 会形成 QK^T 的大矩阵，长序列下中间结果读写很重。FlashAttention 把 Q/K/V 切块放到更快的片上存储中计算，用在线归一化保证 softmax 数值正确。

IO-aware 推导直觉：普通 attention 的瓶颈不只是 FLOPs，还有 HBM 读写中间矩阵 n × n。FlashAttention 按 block 计算局部 QK^T，边算边维护 softmax 的最大值和归一化分母，避免完整物化注意力矩阵。

追问应对：它不是稀疏注意力，也不是把复杂度从 O(n^2) 变成 O(n)。它优化的是 IO 和显存占用，所以长上下文仍然要配合上下文压缩、检索和调度策略。

Q7：GPTQ 和 AWQ 量化差异怎么讲？量化

口语稿：GPTQ 和 AWQ 都是常见的权重量化方法，目标是把模型权重压到 INT4/INT8 等低比特，降低显存和带宽成本。GPTQ 更强调基于二阶近似的逐层误差补偿，AWQ 更强调保护激活敏感的关键权重通道。

GPTQ：通常用校准数据估计量化误差，通过近似 Hessian 信息做误差补偿，让低比特权重尽量接近原模型输出。

AWQ：观察到少量权重通道对激活影响很大，因此通过缩放和通道保护减少量化损失，实践中常见于高效部署。

量化目标：核心是让量化后输出误差尽量小，可粗略写成 min ||WX - W_qX||。GPTQ 更关注二阶误差补偿，AWQ 更关注保护激活敏感通道。

工程评估：量化后不能只看困惑度。要看业务集准确率、格式遵循、拒答率、长推理稳定性、吞吐、显存、P99 和回滚成本。

Q8：INT4 量化一定比 FP16 更快吗？陷阱题

口语稿：不一定。量化能显著降低显存占用和带宽压力，但是否更快取决于硬件、kernel、batch、模型结构和反量化开销。

工程判断：如果瓶颈是显存容量或内存带宽，量化收益明显；如果 kernel 不成熟、batch 很小、反量化开销占比高，速度提升可能有限甚至变慢。

追问应对：我会先用真实请求压测 FP16/BF16、INT8、INT4，不只看单条样例。关注 TTFT、TPOT、吞吐、质量掉点和显存余量。

Q9：prefill 和 decode 为什么要分开优化？服务拆解

口语稿：prefill 是对 prompt 的并行计算，通常算力密集；decode 是逐 token 生成，通常更受 KV Cache、显存带宽和调度影响。两阶段瓶颈不同，所以优化手段也不同。

工程手段：prefill 可通过 prompt 缓存、chunked prefill、上下文裁剪、FlashAttention 优化；decode 可通过 continuous batching、KV Cache 管理、GQA/MQA、speculative decoding 优化。

追问应对：如果用户抱怨“打开慢”，重点看 TTFT 和队列等待；如果抱怨“流式输出慢”，重点看 TPOT、decode batch 和 GPU 利用率。

Q10：推理服务上线怎么做容量评估？项目落地

口语稿：容量评估要把请求数转成 token 数，因为 LLM 成本主要和输入/输出 token、并发、模型大小、精度和 SLA 有关。

指标口径：统计 QPS、输入 token P50/P95、输出 token P50/P95、峰值并发、TTFT、TPOT、P95/P99、错误率、超时率、GPU 利用率、显存水位。

项目落地：压测时要混合短请求和长请求，模拟真实长度分布。只用固定长度 prompt 压测会高估线上表现。

九、深挖分布式训练：Megatron-LM、DeepSpeed、FSDP、TP、PP

本章逻辑：先估训练显存和吞吐瓶颈；如果模型状态冗余高，用 ZeRO/FSDP；如果单层矩阵太宽，用 TP；如果层数太深或整模型放不下，用 PP；如果单一策略不够，就组合成 TP + PP + DP/FSDP 的混合并行。

Q11：为什么大模型训练需要并行？总纲

口语稿：单卡放不下模型参数、优化器状态、梯度和激活，也无法在可接受时间内完成训练，所以需要数据并行、张量并行、流水线并行、ZeRO/FSDP 等混合方案。

显存构成：训练显存主要来自参数、梯度、优化器状态、激活、临时 buffer。Adam 优化器会带来额外一阶/二阶矩状态，显存压力远高于推理。

选型思路：数据并行解决吞吐，张量并行解决单层太大，流水线并行解决层数太深，ZeRO/FSDP 解决状态冗余。

从现象到方案：OOM 发生在模型加载或 optimizer 初始化 -> 优先考虑 ZeRO/FSDP 分片状态；单层 GEMM 太大或单层计算慢 -> 考虑 TP；模型层数深、整模型放不下 -> 考虑 PP。

Q12：张量并行 TP 的核心是什么？重点

口语稿：TP 是把单层里的大矩阵切到多张 GPU 上共同计算。例如 Transformer 里的线性层可以按列切或按行切，每张卡算一部分，再通过 all-reduce 或 all-gather 合并结果。

Megatron 视角：Megatron-LM 经典做法是对 MLP 和 attention 的大矩阵做列并行、行并行组合，尽量减少通信点，同时保持数学等价。

矩阵切分直觉：列并行可理解为把 Y = XA 的权重 A 按输出维切开，每张卡算一部分输出；行并行可理解为按输入维切开，每张卡算部分乘积，最后 all-reduce 求和。

代价：TP 通信频繁，依赖高速互联。TP 跨节点会很贵，通常优先放在同机 NVLink/NVSwitch 内。

追问应对：TP 适合“单层太宽，单卡算不下或算不快”的情况；但 TP 度数不是越大越好，通信会吞掉收益。

Q13：流水线并行 PP 的核心是什么？重点

口语稿：PP 是把模型按层切成多个 stage，每个 stage 放在不同 GPU 上。训练时把 batch 切成 micro-batch，像流水线一样让不同 stage 同时处理不同 micro-batch。

关键问题：PP 最大问题是 pipeline bubble，也就是有些 stage 在等待前后 stage，GPU 空转。micro-batch 越多，bubble 占比越低，但调度和激活显存压力也会变化。

bubble 直觉：若 pipeline stage 数为 p，micro-batch 数为 m，简单流水线的空泡占比近似随 (p-1)/(m+p-1) 增大而变差。micro-batch 越多，空泡越小。

常见策略：GPipe 使用先全 forward 后全 backward；1F1B 调度让 forward/backward 交错，减少显存和空泡。

追问应对：PP 适合模型层数深、整模型放不下的情况；切分时要让每个 stage 计算量接近，否则会负载不均。

Q14：DeepSpeed ZeRO 三个阶段怎么讲？高频

口语稿：ZeRO 的思想是把数据并行中每张卡重复保存的训练状态切分掉，逐步分片优化器状态、梯度和参数。

  • ZeRO-1：分片优化器状态，降低 Adam 状态冗余。
  • ZeRO-2：继续分片梯度，进一步省显存。
  • ZeRO-3：连参数也分片，需要时再 gather，显存省最多，通信和调度更复杂。
分片原理：普通 DP 每张卡都有完整参数、梯度、优化器状态；ZeRO 把这些状态按 data parallel rank 切开，需要计算时再通信恢复局部所需内容。

追问应对：ZeRO-3 不是免费午餐。模型越大越有价值，但通信、参数 gather、checkpoint 和调试复杂度都会上升。

Q15：FSDP 和 ZeRO 的关系是什么？PyTorch

口语稿：FSDP 可以理解为 PyTorch 生态里对参数、梯度、优化器状态进行全分片训练的方案，思想上接近 ZeRO-3。它在 forward 前 all-gather 参数，计算后释放，backward 时再按需处理梯度。

FSDP 流程：forward 前 all-gather 当前模块完整参数 -> 计算 forward -> 释放非本地参数分片 -> backward 时再次 gather 或使用保存策略 -> 梯度 reduce-scatter 回各 rank。

工程关注：FSDP 要关注 auto wrap policy、sharding strategy、activation checkpointing、mixed precision、state dict 保存方式和恢复速度。

选型话术：DeepSpeed 生态成熟、配置能力强；FSDP 更贴近 PyTorch 原生，和 torch.compile、原生 checkpoint 等集成更自然。最终看团队栈和训练规模。

Q16：Megatron-LM 主要解决什么？框架

口语稿：Megatron-LM 是面向超大 Transformer 训练的高性能框架，核心能力是张量并行、流水线并行、序列并行和混合并行，把模型切到大量 GPU 上高效训练。

项目理解：它不是只提供“启动脚本”，而是把 Transformer 结构和并行策略深度耦合，例如 attention/MLP 的矩阵切分、通信点设计、pipeline 调度。

追问应对：如果问“为什么不用普通 DDP”，答：DDP 每卡有完整模型，模型太大时放不下；即使放得下，单层计算也可能成为瓶颈，TP/PP 才能继续扩展。

Q17：混合并行怎么设计？系统设计

口语稿：混合并行通常把 TP 放在高速互联范围内，把 PP 跨更大的模型层级切分，再用 DP/FSDP 扩吞吐。目标是让显存放得下、通信不过载、每张卡负载均衡。

示例：假设 64 卡训练，可以按 TP=4、PP=4、DP=4 组织。每个 pipeline stage 内 4 卡做张量并行，4 个 stage 串成模型，再复制 4 份做数据并行。

从现象到方案：单用 DP 显存放不下 -> 加 ZeRO/FSDP；单层仍然太宽 -> 加 TP；模型太深且激活/参数跨层放不下 -> 加 PP；通信太慢 -> 调整并行维度和拓扑映射。

追问应对：并行度要通过 profile 调整。看到 GPU 利用率低，可能是 pipeline bubble、通信阻塞、数据加载慢、checkpoint 太频繁或 batch 设置不合理。

Q18：训练吞吐上不去怎么排查？排障

口语稿：先区分是计算瓶颈、通信瓶颈、数据瓶颈还是调度瓶颈。不要只看 loss，要同时看 tokens/s、MFU、GPU 利用率、通信耗时、data loader 等待和显存水位。

排查路径：单卡 profile 算子效率，多卡看 all-reduce/all-gather 时间，PP 看 stage idle，数据侧看 dataloader 队列和样本长度分布。

常见修复：增大 global batch、调 micro-batch、开启 activation checkpointing、通信计算重叠、调整 TP/PP、清洗超长样本、优化 checkpoint 间隔。

十、深挖模型理论：Transformer、RoPE、Scaling Law、MoE

本章逻辑：模型能力来自结构、数据、参数、计算和训练目标共同作用；Transformer 解决可扩展建模，RoPE 解决位置表达，scaling law 解释规模收益，MoE 试图用稀疏激活扩大容量，长上下文治理解决信息密度和成本问题。

Q19：Transformer Block 细节怎么讲？基础必会

口语稿：典型 decoder-only Transformer block 包括归一化、自注意力、残差连接、前馈网络。输入 token embedding 加位置信息后，逐层通过 attention 建模上下文关系，再通过 MLP 做非线性变换。

细节：现代 LLM 常用 Pre-LN、RMSNorm、SwiGLU/GEGLU、RoPE、GQA/MQA、残差连接。Pre-LN 有助于深层训练稳定，RMSNorm 更轻量。

RMSNorm：RMSNorm(x) = x / sqrt(mean(x^2) + eps) * g。它不减均值，只按均方根缩放，计算更轻，常用于 LLaMA 类模型。

追问应对：如果问“attention 和 MLP 分别做什么”，可以说 attention 负责 token 间信息路由，MLP 负责每个位置上的特征变换和知识存储。

Q20：多头注意力为什么需要多个头？高频

口语稿：多头注意力让模型在不同子空间里关注不同关系，例如语法依赖、实体指代、局部窗口、长程依赖。多个头不是简单复制，而是提高表示多样性。

公式：head_i = Attention(QW_i^Q, KW_i^K, VW_i^V)，多个 head 拼接后再线性投影。

工程追问：头数越多不一定越好。头数增加会影响维度切分、KV Cache、并行效率和模型质量，现代推理常用 GQA/MQA 降低 K/V 成本。

Q21：RoPE 的本质是什么？位置编码

口语稿：RoPE 是旋转位置编码，它把位置信息通过旋转矩阵注入 Q/K，使注意力分数天然包含相对位置信息，因此在 decoder-only LLM 中很常见。

直觉：不同位置对应不同旋转角度，两个 token 的相对距离会反映在 Q 和 K 的点积里。相比绝对位置 embedding，它对长度外推更友好。

追问应对：RoPE 不等于无限长上下文。长上下文还会遇到注意力稀释、检索噪声、训练长度外推不足等问题，需要 NTK scaling、YaRN、位置插值或训练阶段扩长配合。

Q22：Scaling Law 怎么讲？理论

口语稿：Scaling law 描述模型性能随参数量、数据量、计算量扩大而呈现可预测改善。它的价值是指导资源分配：给定算力预算时，模型太大但数据不足，或者数据太多但模型太小，都不是最优。

经验形式：Loss(N,D,C) ≈ A/N^α + B/D^β + E，其中 N 是参数量，D 是训练 token 数，C 是计算预算，E 是不可约误差。

关键点：Chinchilla 风格结论强调 compute-optimal：参数和训练 token 要匹配。很多能力不是魔法突然出现，而是在规模、数据质量、训练目标共同作用下逐步增强。

从现象到方案：模型大但效果提升小 -> 检查训练 token 是否不足、数据质量是否低、是否过拟合重复数据 -> 用 scaling law 思想重新平衡参数量、数据量和计算预算。

追问应对：Scaling law 是经验规律，不保证所有任务、所有数据、所有架构都同样成立。数据质量、去重、课程学习、对齐方式会显著影响结果。

Q23：MoE 架构的核心收益和风险？架构

口语稿：MoE 用多个专家网络扩大总参数量，但每个 token 只激活少数专家，因此在计算量相对可控的情况下提升模型容量。

核心模块：router 根据 token 表示选择 top-k expert；expert 通常是 FFN；还需要 load balancing loss 避免所有 token 挤到少数专家。

路由形式：p = softmax(W_r x)，选择 top-k expert，输出可写成 y = Σ_{i in top-k} p_i E_i(x)。
负载均衡：如果 router 总选少数 expert，那些 expert 会过载，其他 expert 学不到东西。load balancing loss 会惩罚路由分布过度集中。

工程风险：MoE 会带来路由不均、专家负载倾斜、跨卡 all-to-all 通信、训练不稳定、推理部署复杂等问题。

追问应对：MoE 不是“免费变大”。如果 batch 小、路由分散或通信慢，推理效率可能不如 dense 模型。

Q24：长上下文为什么容易退化？长上下文

口语稿：上下文变长后，模型能看到更多信息，但有效信息密度下降，注意力更容易被噪声干扰，且位置外推、KV Cache 和计算成本都会变差。

项目落地：不要把长上下文当万能方案。生产里更常用 RAG、重排、摘要、证据压缩、结构化上下文和引用校验，提高“有效 token 比例”。

追问应对：评估长上下文要看 needle-in-haystack、真实任务成功率、引用准确率、成本和延迟，不只看最大窗口长度。

Q25：为什么 LLM 常用 BF16 而不是 FP16？数值稳定

口语稿：BF16 指数位更宽，动态范围接近 FP32，比 FP16 更不容易溢出，适合大模型训练。FP16 精度更细一点但动态范围小，训练中更容易出现 overflow。

工程追问：混合精度训练还要配合 loss scaling、梯度裁剪、异常检测。看到 loss NaN，要查学习率、数据异常、归一化、混精溢出和梯度爆炸。

十一、深挖 RL 算法与对齐：PPO、GRPO、GSPO、奖励设计和稳定性

本章逻辑：先定义你真正想优化的目标，再设计 reward；reward 只是代理目标，所以要用 KL、clip、entropy、回归集和人工抽样防止模型跑偏；PPO 强在通用稳定，GRPO 强在组内比较，DPO 强在工程简单。

本章关键名词先解释清楚

真正想优化的目标：业务或任务的真实效果，例如数学题答对率、代码测试通过率、回答有帮助且安全、Agent 工具调用成功率。它是最终目标，不一定能被一个训练 loss 完整表达。

reward：训练时给模型输出打的分，是对真实目标的近似。比如答案正确 +1，格式正确 +0.1，输出太长 -0.2。reward 方便优化，但它只是“代理指标”，不是最终质量本身。

KL：衡量当前模型和参考模型输出分布差多远。KL 太高说明模型为了拿 reward 偏离原模型太多，可能开始胡编、格式怪异或能力退化。

clip：PPO 里的“更新限幅”。如果新策略相对旧策略变化太大，就把收益截断，避免一次更新把模型推崩。

entropy：输出分布的多样性或不确定性。entropy 太低说明模型过早变得死板，容易模式坍缩；太高则可能输出太随机。

回归集：固定的一组验证题/样本，每次训练后都跑一遍，用来确认新模型没有把旧能力训坏，例如格式遵循、基础问答、安全拒答、数学正确率。

人工抽样：从训练结果里抽一批样本人工看，尤其看高 reward 但低质量、低 reward 但其实正确的样本，用来发现 reward hacking 和评测错配。

Q26：LLM 对齐里的 RL 在优化什么？总纲

口语稿：LLM 对齐里的 RL 不是让模型玩游戏，而是把“回答是否符合偏好、是否正确、是否安全、格式是否合规”等目标转成奖励信号，用策略优化让模型更倾向产生高奖励回答。

基本链路：SFT 让模型会按指令回答；奖励模型或规则奖励提供偏好信号；PPO/GRPO/GSPO 等算法更新策略；KL 约束防止模型偏离参考模型太远。

Policy Gradient 基本式：∇J(θ) = E[∇ log π_θ(a|s) A(s,a)]。意思是：如果某个动作的 advantage 为正，就提高它在该状态下的概率；为负就降低概率。
从现象到方案：SFT 回答格式对但偏好不稳定 -> 引入偏好数据或 reward；reward 能拉动行为但可能过优化 -> 加 KL、clip、回归集和人工抽样；推理题能自动判分 -> 考虑 GRPO 组内比较。

追问应对：如果被问“你做的 RL 到什么程度”，不要只说“我了解 PPO/GRPO”。建议按下面 5 层回答：

第一层，先定边界：“我主要做的是 LLM 对齐/推理任务里的 RL 工程，不是通用机器人控制 RL。重点在 reward 设计、训练稳定性、曲线分析和模型效果评估。”

第二层，说任务：“我会选可验证任务练手，比如数学推理、代码生成、格式化问答或工具调用。每个 prompt 采样多条回答，用正确性、格式、长度、安全等信号打 reward。”

第三层，说 reward 项：“例如数学题 reward 可以拆成：最终答案正确性、推理格式、过程完整性、长度惩罚、重复惩罚、KL 惩罚。这样能解释模型为什么被鼓励做某种行为。”

第四层，说曲线和调参：“训练时我不只看 reward，还会看 KL、entropy、response length、成功率、format error、人工抽样。如果 KL 飙升就提高 KL 系数或降学习率；如果 entropy 快速下降就加强探索或减小更新步长；如果长度变长但正确率不升，就检查 reward 是否鼓励啰嗦。”

第五层，说失败复盘：“我会准备一个失败例子，比如 reward 上升但人工评估下降，定位到格式奖励或长度奖励过强，然后降低该项权重、加入长度惩罚、增加 holdout 回归集，再对比修复前后的曲线和样本。”

可直接背的回答：“我的 RL 深度主要在 LLM 对齐工程层：能搭 SFT 后的 PPO/GRPO/DPO 类训练流程，能设计可解释的 reward，能看 reward、KL、entropy、长度和成功率曲线，也能复盘 reward hacking、熵崩溃、KL 失控这类问题。我不会把自己包装成底层 RL 理论专家，但能把算法用在具体任务里并解释调参依据。”

Q27：PPO 核心思想怎么讲？高频

口语稿：PPO 的核心是限制策略每次更新不要离旧策略太远。它用 clipped objective 裁剪新旧策略概率比，在提升奖励的同时避免训练突然崩掉。

直觉：如果新策略相对旧策略的概率比 r_t 超出 1 +/- epsilon，就限制这部分收益，防止过大更新。
目标函数：L^CLIP = E[min(r_t A_t, clip(r_t, 1-ε, 1+ε) A_t)]，其中 r_t = π_θ(a_t|s_t) / π_old(a_t|s_t)。

推导直觉：r_t 表示新策略相对旧策略把同一动作概率放大了多少。优势 A_t 为正时希望放大概率，但不能放太多；优势为负时希望降低概率，也不能一步降崩。

LLM 场景：通常会有 policy model、reference model、reward model、value model。reward 给方向，value 估计优势，KL 控制偏移。

追问应对：PPO 稳但成本高，因为需要采样、奖励打分、价值估计和多轮更新；on-policy 数据复用效率有限。

Q28：GRPO 的创新点是什么？推理对齐

口语稿：GRPO 的核心是对同一个 prompt 采样一组回答，用组内相对奖励构造 advantage，减少对单独 value model 的依赖，适合数学、代码、推理这类可以做组内比较的任务。

为什么有用：如果同题采样多条轨迹，有的正确、有的错误，就可以用组内均值和方差做归一化，让模型学习“相对更好的推理路径”。

组内 advantage：A_i = (r_i - mean(r_group)) / (std(r_group) + eps)。同一题多条回答内部比较，减少不同题目难度差异造成的 reward 尺度问题。

常见奖励：正确性奖励、格式奖励、过程约束、长度惩罚、重复惩罚、KL 惩罚。数学题常把最终答案正确性作为主奖励，格式作为辅助奖励。

追问应对：GRPO 的风险是奖励噪声和采样质量。若组内样本都很差或奖励器误判，更新信号会偏。

Q29：GSPO 怎么理解？进阶

口语稿：GSPO 可以按“序列级策略优化”理解：相比只在 token 级别看概率比，它更关注整条回答序列的优化稳定性，适合长推理场景中减少 token 级噪声带来的不稳定。

和 GRPO 的关系：二者都可以利用组内采样和相对优势。GRPO 更常被描述为 group relative advantage；GSPO 更强调 sequence-level objective，让更新信号和完整回答质量更一致。

面试边界：如果没有亲自实现底层算法，不要硬说自己改过公式。可以说理解其动机：长链路推理中 token 级奖励稀疏、方差高，因此希望用更稳定的组内/序列级信号做策略更新。

Q30：reward 怎么设计才像做过项目？重点

口语稿：reward 设计要从业务目标拆解，不是只给一个总分。一般会把正确性、格式、可读性、安全、工具调用、长度和成本拆成多项奖励，再做权重和约束。

示例：数学推理可设 R = 答案正确 + 格式合规 + 推理步骤完整 - 重复惩罚 - 过长惩罚 - KL惩罚。Agent 任务可加工具调用成功率、参数正确性、最终任务完成度。

追问应对：奖励项要能被验证。凡是无法稳定自动评估的项，要么引入人工偏好/模型裁判并做一致性校验，要么降低权重，避免模型钻空子。

Q31：reward hacking / 奖励劫持是什么？怎么解决？高频

口语稿：奖励劫持是模型学会了拿高 reward 的捷径，但没有真正提升任务质量。例如为了格式分重复模板、为了长度奖励堆废话、为了裁判偏好写看似严谨但错误的解释。

定位方法：看 reward 上升但人工评测或真实成功率不升；抽样高 reward 低质量样本；比较各 reward 子项是否某一项异常主导。

从现象到方案：reward 上升但真实效果下降 -> reward 不是目标本身而是代理目标 -> 抽样高分坏样本，拆 reward 子项 -> 降低可钻空子项权重、增加反作弊和 holdout。

解决：重构奖励、增加反作弊规则、引入多维评测、限制单项奖励上限、加入 KL/长度惩罚、维护 holdout 回归集，并定期人工审查高分样本。

Q32：熵崩溃是什么？怎么解决？训练稳定

口语稿：熵崩溃是策略输出分布过早变得很尖锐，模型不再探索，回答模式单一，容易陷入局部最优。曲线上通常表现为 entropy 快速下降、KL 异常、输出多样性变差。

熵公式：H(p) = -Σ_i p_i log p_i。分布越均匀，熵越高；概率集中到少数 token，熵越低。

原因：学习率太大、奖励过强、KL 约束太弱、采样温度过低、训练数据过窄、某类格式奖励被过度放大。

解决：降低学习率、增加 entropy bonus、加强 KL 控制、调高采样温度、扩大 prompt 多样性、裁剪奖励、缩短每轮更新步数。

Q33：训练几个模型后，loss 曲线应该怎么看？实战

口语稿：RL 对齐不能只看一个 loss。要联合看 reward、KL、entropy、clip fraction、policy loss、value loss、response length、任务成功率和人工评测。

常见现象：reward 上升但 KL 失控，说明模型偏离参考太远；entropy 快速下降，可能探索不足；value loss 抖动大，可能 critic 学不好；长度持续变长，可能奖励鼓励啰嗦。

追问应对：如果指标波动，先确认数据和评测是否稳定，再查学习率、batch size、reward scale、KL coefficient、采样温度和异常样本。

Q34：PPO、GRPO、DPO 怎么选？选型

口语稿：DPO 链路简单，适合有高质量 chosen/rejected 偏好对时快速对齐；PPO 更通用，适合复杂奖励和在线探索，但成本高；GRPO 适合同题多采样、可自动验证的推理任务。

工程判断：如果资源紧张，先 SFT + DPO 建 baseline；如果有规则奖励和可验证答案，再尝试 GRPO；如果需要复杂 reward model、在线反馈和价值函数估计，再考虑 PPO。

Q35：实际训练时哪些超参数最关键？调参

口语稿：关键超参数包括学习率、batch size、rollout 数、每个 prompt 采样条数、KL coefficient、clip range、reward scale、max response length、temperature、top-p 和梯度裁剪。

调参顺序：先固定数据和评测集，调 reward scale 和 KL，让模型不跑飞；再调学习率和 batch 稳定曲线；最后调采样和长度，提高探索和任务收益。

Q36：如何证明 RL 训练真的有效？面试闭环

口语稿：要用多层评估证明：训练 reward 只是内部信号，最终要看离线任务成功率、holdout 泛化、人工偏好、格式错误率、安全问题、长度成本和线上灰度指标。

项目说法：我会保留固定回归集，每次训练后对比 SFT baseline、DPO baseline 和 RL 模型，抽样分析高分错误、低分正确、奖励冲突样本，再决定是否进入灰度。

十二、指标与曲线：看到波动要能解释

本章逻辑：指标不是为了好看，而是为了定位因果。推理指标回答“用户为什么慢”；训练指标回答“模型为什么不收敛或效率低”；RL 指标回答“模型是不是为了 reward 跑偏”。

推理服务指标

  • TTFT：首 token 延迟，受排队、prefill、调度影响。
  • TPOT：每 token 延迟，反映 decode 阶段速度。
  • P95/P99：长尾体验，常被长请求、队列阻塞、显存抢占拉高。
  • Throughput：tokens/s 比 QPS 更适合衡量 LLM 服务。
  • GPU 利用率：低不一定是坏事，要结合队列和 SLA 看。

训练稳定指标

  • loss：下降不代表业务必然提升，要看验证集和任务指标。
  • grad norm：异常尖峰可能是脏数据、学习率过大或数值溢出。
  • tokens/s：训练吞吐，和并行策略、数据加载、通信相关。
  • MFU：模型 FLOPs 利用率，用于判断训练效率。
  • NaN/Inf：优先查混精、学习率、异常样本和归一化。

RL 对齐指标

  • reward：方向信号，不等于真实质量。
  • KL：衡量策略偏离参考模型的程度。
  • entropy：反映探索和输出多样性。
  • clip fraction：PPO 更新被裁剪比例，过高说明步子太大。
  • response length：长度异常变化常暗示奖励被钻空子。

常见曲线异常怎么解释？

reward 升、准确率不升：奖励错配或 reward hacking，抽样高 reward 样本排查。

KL 突然升高：学习率过大、KL 系数太低、reward scale 太强或异常 batch。

entropy 快速归零：探索崩溃，调低更新强度、提高 KL/entropy 约束。

P99 高但平均低：长尾请求、长度分布、队列等待或 batch 调度不合理。

GPU 利用率低：可能是数据加载慢、通信阻塞、batch 太小、pipeline bubble 或服务等待请求。

指标口径专业版

TTFT：TTFT = request_start 到 first_token_time，包含排队、调度、prefill 和首步 decode。
TPOT：TPOT ≈ (finish_time - first_token_time) / output_tokens，衡量流式生成阶段每个 token 的平均耗时。
吞吐：tokens/s = (input_tokens + output_tokens) / wall_time，推理服务常分 prefill throughput 和 decode throughput。
MFU：MFU = 实际模型 FLOPs / 理论峰值 FLOPs，用于判断训练是否有效利用硬件。

面试提醒：P99 和平均值要一起看。平均值好看但 P99 差，说明少量长尾请求已经破坏用户体验。

十三、项目中怎么讲：把技术和经历连起来

1. 推理服务怎么讲成项目能力？

可以说：我不会把 vLLM 只当成“换一个推理框架”，而是先分析服务 SLA 和 token 分布，再决定是否引入 PagedAttention、continuous batching、量化和缓存。比如智慧教育/Agent 场景里，用户请求长度差异大、并发波峰明显，就要关注 TTFT、P99、队列长度和显存水位。

可复述模板：问题背景是高峰时推理超时和成本高；方案是按模型大小和任务价值分层路由，长请求做上下文压缩，推理引擎用 vLLM 提升并发，关键指标看超时率、P99、tokens/s 和 GPU 利用率；副作用是长请求可能拉高尾延迟，需要限流、优先级和超时取消。

2. 分布式训练怎么讲到“掌握程度”？

可以说：我理解 Megatron-LM、DeepSpeed、FSDP 的核心差异，重点掌握 TP/PP 的切分逻辑和通信代价。实际项目如果没有训千亿模型，也可以诚实表达为“能读懂配置、能解释为什么这样切、能根据显存和吞吐排查问题”。

可复述模板：单卡放不下时先估算参数、梯度、优化器和激活显存；单层太大用 TP，层数太深用 PP，状态冗余用 ZeRO/FSDP；调优看 tokens/s、MFU、通信耗时、stage idle 和 loss 稳定性。

3. RL 训练怎么讲得可信？

可以说：我实际训练时会先做 SFT baseline，再设计 reward，跑 PPO/GRPO 类实验，对比 reward、KL、entropy、成功率和人工抽样。重点不是只说算法名，而是能说明一次失败如何修。

可复述模板：我遇到过 reward 上升但答案变啰嗦的问题，定位后发现格式/长度相关奖励过强，于是降低该项权重、增加长度惩罚和人工 holdout，对比后任务准确率恢复，平均输出长度下降。

十四、易混淆概念对比：小白最容易卡在这里

1. 训练 vs 推理

概念在做什么关注指标一句话记忆
训练用数据更新模型参数loss、tokens/s、显存、稳定性、验证集效果让模型“学会”
推理用已有参数生成答案TTFT、TPOT、P99、吞吐、成本、错误率让模型“好好服务用户”

2. prefill vs decode

阶段发生在什么时候像什么常见瓶颈
prefill生成第一个 token 前读完整道题prompt 太长、排队、attention 计算
decode开始逐 token 输出后一个字一个字写答案KV Cache、显存带宽、batch 调度

3. 吞吐 vs 延迟

吞吐：系统整体单位时间能处理多少 token，像“餐厅一小时能做多少单”。

延迟：单个用户等多久，像“我这一单多久能上菜”。

取舍：batch 变大可能提高吞吐，但个别用户可能等更久，所以线上要同时看吞吐和 P95/P99。

4. TP vs PP vs DP

方式核心动作小白类比什么时候用
DP复制模型，分数据多个人做不同试卷，最后同步答案模型单卡能放下，想提高吞吐
TP拆一层矩阵一道大题太宽，几个人分块算单层太大、矩阵计算太重
PP拆不同层流水线工厂，每个人负责一段工序模型很深、整模型单卡放不下

5. FSDP vs DeepSpeed ZeRO

共同点：都想减少多卡训练中的状态冗余，把参数、梯度、优化器状态分散保存。

区别：FSDP 是 PyTorch 原生路线，更贴近官方生态；DeepSpeed ZeRO 是 DeepSpeed 体系里的核心能力，配置和工程功能更丰富。

面试表达：不要死记“谁更好”，要说清楚团队栈、训练规模、调试成本、checkpoint、通信开销和生态支持。

6. PPO vs GRPO vs DPO

算法需要什么数据/信号优势风险
PPOreward、rollout、value/KL通用，能处理复杂奖励训练链路重，调参复杂
GRPO同题多回答的组内比较适合可验证推理任务，少依赖 value model奖励噪声和采样质量影响大
DPOchosen/rejected 偏好对简单稳定，工程成本低探索能力弱，依赖偏好数据质量

指标异常速查

TTFT 高：查 prompt 长度、排队、prefill、限流、模型冷启动。

TPOT 高：查 decode batch、KV Cache、显存带宽、GPU 利用率。

loss NaN：查学习率、混精溢出、脏数据、梯度爆炸、归一化。

reward 上升但效果下降：查 reward hacking、评测集泄漏、单项奖励权重过大。

entropy 过快下降：查学习率、KL 约束、采样温度、奖励过强、训练数据太窄。

十五、指标因果树：看到问题怎么一路查下去

1. 推理服务：P99 高怎么查？

P99 高 -> 先拆 TTFT 和 TPOT。

TTFT 高：排队时间长 -> 看并发、限流、队列长度；prefill 慢 -> 看 prompt 长度、chunked prefill、FlashAttention；冷启动慢 -> 看模型加载和实例预热。

TPOT 高：decode 慢 -> 看 KV Cache 读写、batch token 数、显存带宽；长请求拖累短请求 -> 看 continuous batching、长度分桶、优先级队列。

面试表达：我不会直接说“上 vLLM 就好了”，而是先拆首 token 和流式 token，再根据瓶颈决定是调度、KV 管理、上下文裁剪还是量化。

2. 分布式训练：吞吐低 / GPU 利用率低怎么查？

GPU 利用率低 -> 先看是不是数据没喂上、通信在等、pipeline 有空泡、batch 太小。

数据瓶颈：dataloader 等待高 -> 增加 worker、预取、缓存、样本打包。

通信瓶颈：all-reduce/all-gather 时间高 -> 调整 TP/DP 维度、拓扑映射、通信计算重叠。

PP 空泡：stage idle 明显 -> 增加 micro-batch、调整 stage 切分、使用 1F1B 调度。

面试表达：吞吐低不是一个原因，要按数据、计算、通信、调度四类拆。能拆清楚，说明你真的理解分布式训练。

3. RL 对齐：reward 高但模型变差怎么查？

reward 上升但人工评测下降 -> 先怀疑 reward hacking 或评测错配。

输出变长：可能长度/格式奖励过强 -> 加长度惩罚、限制单项奖励上限。

KL 飙升：策略偏离参考太远 -> 提高 KL coefficient、降低学习率、缩短更新步数。

entropy 快速下降：策略过早确定 -> 加强 entropy bonus、提高采样温度、增加数据多样性。

高分坏样本多：reward 模型或规则有漏洞 -> 人工审查、修 reward、加 holdout 回归集。

面试表达：RL 训练不能只报 reward 曲线。我要同时看 reward、KL、entropy、长度、成功率和人工抽样，才能判断是不是学到了真正能力。

十七、公式速查表：必须会复述的专业表达

主题公式 / 口径一句话解释
语言模型目标P(x_1...x_T)=Π_t P(x_t|x_<t)整段文本概率拆成逐 token 条件概率。
Softmaxp_i=exp(z_i)/Σ_j exp(z_j)把 logits 转成概率分布。
交叉熵L=-log p(y)真实 token 概率越低，惩罚越大。
梯度下降θ_new=θ-η∇L沿着让 loss 下降的方向更新参数。
Attentionsoftmax(QK^T/sqrt(d_k))V用 Q/K 算关注权重，再对 V 加权汇总。
KV Cache 显存B×S×L×2×H_kv×D_head×bytesbatch、长度、层数、KV 头数都会推高显存。
RoPE<R_mq,R_nk>=<q,R_{n-m}k>绝对旋转转成相对距离信息。
Pipeline bubble(p-1)/(m+p-1)stage 越多、micro-batch 越少，空泡越明显。
Scaling lawLoss≈A/N^α+B/D^β+E参数和数据增加通常会按经验规律降低 loss。
MoE routingy=Σ_{i in top-k}p_iE_i(x)每个 token 只激活少数专家。
Policy gradient∇J=E[∇logπ(a|s)A]好动作提高概率，坏动作降低概率。
PPO Clipmin(rA,clip(r,1-ε,1+ε)A)限制策略单步更新幅度。
GRPO AdvantageA_i=(r_i-mean(r))/std(r)同题多回答做组内相对比较。
EntropyH=-Σp log p衡量输出分布多样性，过低可能模式坍缩。
KLKL(p||q)=Σp log(p/q)衡量新策略偏离参考策略多远。

公式怎么背才不死记？

每个公式都按三句话背：它在衡量什么、为什么要这样设计、指标变大或变小代表什么。比如 KL 不是“一个数学公式”，而是“防止新模型为了 reward 跑离原模型太远”的约束。
